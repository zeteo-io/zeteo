Row rules. A grant now says which rows it reaches: `row_access` is `unlimited_default` (the default), `all` or `rule`, and a `rule` carries a `row_rule` in the query language's `where` syntax over the grant's own table (any operator, relative dates, `and`/`or`/`not`), which may compare a column with the caller's own identity values under a named key (`{ "identity": "netsuite_employee_id" }`) and may name a column the grant does not include. Over all the grants reaching a caller on a table, any `all` grant gives every row, else the rules are OR'd, else every row, as before. Rules are enforced on every read of a table: `POST /v1/query`, `POST /v1/export`, MCP, saved queries, dashboard panels, joins, measures and metrics; the resolved rule is part of the plan, so the dashboard cache never shares an entry between viewers with different rules. Fails closed: a caller with no value under a key a rule names gets no rows from that grant, and a rule whose column has gone missing or that resolves to over 50,000 values refuses the query with `409 row_rule_unavailable`. New: `/v1/identity-keys` (list, create, change, delete; `/values` list, add up to 1,000 at a time, remove; `/missing`, the people a rule reaches who hold no value) and `GET /v1/grants/effective` (one user's combined columns, rows, grants and warnings for one table). Grants gain `row_access`, `row_rule`, `row_rule_description` and `row_rule_problems`; **`PUT /v1/grants/:id` now requires `row_access`**, so a body of columns only is a `400`. New errors `invalid_row_rule`, `identity_key_in_use`, `identity_value_taken` and `row_rule_unavailable`. Callers are told their rows are limited: `rows_limited` on query, saved-query run, saved-panel preview, measure and metric preview and dashboard panel results, `X-Zeteo-Rows-Limited` on exports, `rows_limited` and `rows_limited_reason` (in words, naming only granted columns and identity keys by label) on catalogue tables, `list_tables` and `describe_table`, and MCP `query`, `run_saved_query`, `preview_panel` and `card_panel_rows`, plus a line in the per-caller MCP instructions. Audit events `zeteo.identity_key.*` and `zeteo.identity_value.*`; the grant events carry the rule, and a source transfer resets rows on the new owner's earlier grant (`row_access_reset`). The admin UI gains the Rows section and condition builder in the grant dialog, Effective access, and an Identities page (keys, values with bulk paste, people missing a value). An identity reference may say `below: true` (`{ "identity": "rep_id", "below": true }`): the values of the caller and of everyone below them in Tereo's reporting lines, at any depth, deactivated users included, so a director sees their whole team's rows. Zeteo reads the reporting lines from Tereo (0.8.3 or later; its `user_resolver` role needs `users.read`) only when a rule uses `below`, cached 30 seconds per user; when Tereo cannot answer, a query reading the table is refused with `503 row_rule_unavailable` ("try again shortly"), and a hierarchy Tereo refuses as too large is `409 row_rule_unavailable` (`too_many_values`): never the caller's own rows only, never every row. A service account gets only its own values. Effective access warns `row_rule_unavailable` with reason `hierarchy_unavailable`, and the grant dialog's identity conditions gain "Include people who report to me". Rules do not follow relations. A rule's JSON number that is not the double it parses to, digit for digit (`9007199254740993`, `0.10000000000000001`), or that the double writes with an exponent (`1e21`), is refused with `invalid_row_rule`: write such numbers as decimal strings. A `gt`, `gte`, `lt`, `lte` or `between` bound on a number column with more than 38 digits is refused too. On SQL Server no value is compared with an integer, decimal or money column through a float: an `eq` or `in` (in a rule or a query) leaves out a value the column's catalogued type cannot hold, while a `ne`, a `notIn`, or an `eq` or `in` under a `not` compares it exactly as `decimal(38, s)`, so a column widened since the last refresh still hides its rows; a long list is read in the column's own exact type, and such values in a list per scale. A rule's `ne` or `notIn` on a value of more than 38 digits keeps no row. `__proto__` is refused as a filter path, in queries and rules alike (parsing could not keep it); any other column name, `constructor` and `prototype` included, works. A row rule an upload source's owner writes (without `zeteo.grants.write`) may not use identity values (`400 invalid_row_rule`, with `path` to the reference), and the grant dialog offers an owner no "is one of my …" conditions. A rule on an organization's group counts only when the user is signed in to that organization, as the group's columns do: signed in elsewhere or to none, a grant that does not limit rows gives every row. Effective access says so with the warning `org_scoped_rule_inactive` (the group and its organization, by id and name) and lists the user's groups' `organizations`; its dialog gains an organization picker. Identity values match by the source's own comparison (a collation may ignore case and trailing spaces; numbers compare as numbers), so `POST /v1/identity-keys/:keyId/values` answers `warnings` of `near_duplicate` (`value`, and the other `user_id`) for each new value another user holds up to case, padding or number formatting, and the Add values dialog shows them after saving. Row rules on a Postgres source need PostgreSQL 12 or later: an older server refuses a rule-limited query with `409 row_rule_unavailable` before it runs. A ruled table is read with only the columns the query reads, and the caller's plain conditions on it (a whole conjunct of `where` comparing a column of the from table or an inner-joined table with values of exactly its own type) are applied beside the rule, so its indexes serve them; on SQL Server, references to one table under the same rule share one copy.

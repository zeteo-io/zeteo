Row rules. A grant now says which rows it reaches: `row_access` is `unlimited_default` (the default), `all` or `rule`, and a `rule` carries a `row_rule` in the query language's `where` syntax over the grant's own table (any operator, relative dates, `and`/`or`/`not`), which may compare a column with the caller's own identity values under a named key (`{ "identity": "netsuite_employee_id" }`) and may name a column the grant does not include. Over all the grants reaching a caller on a table, any `all` grant gives every row, else the rules are OR'd, else every row, as before. Rules are enforced on every read of a table: `POST /v1/query`, `POST /v1/export`, MCP, saved queries, dashboard panels, joins, measures and metrics; the resolved rule is part of the plan, so the dashboard cache never shares an entry between viewers with different rules. Fails closed: a caller with no value under a key a rule names gets no rows from that grant, and a rule whose column has gone missing or that resolves to over 50,000 values refuses the query with `409 row_rule_unavailable`. New: `/v1/identity-keys` (list, create, change, delete; `/values` list, add up to 1,000 at a time, remove; `/missing`, the people a rule reaches who hold no value) and `GET /v1/grants/effective` (one user's combined columns, rows, grants and warnings for one table). Grants gain `row_access`, `row_rule`, `row_rule_description` and `row_rule_problems`; **`PUT /v1/grants/:id` now requires `row_access`**, so a body of columns only is a `400`. New errors `invalid_row_rule`, `identity_key_in_use`, `identity_value_taken` and `row_rule_unavailable`. Callers are told their rows are limited: `rows_limited` on query, saved-query run, saved-panel preview, measure and metric preview and dashboard panel results, `X-Zeteo-Rows-Limited` on exports, `rows_limited` and `rows_limited_reason` (in words, naming only granted columns and identity keys by label) on catalogue tables, `list_tables` and `describe_table`, and MCP `query`, `run_saved_query`, `preview_panel` and `card_panel_rows`, plus a line in the per-caller MCP instructions. Audit events `zeteo.identity_key.*` and `zeteo.identity_value.*`; the grant events carry the rule, and a source transfer resets rows on the new owner's earlier grant (`row_access_reset`). The admin UI gains the Rows section and condition builder in the grant dialog, Effective access, and an Identities page (keys, values with bulk paste, people missing a value). `below` (the caller and everyone who reports to them) is not available yet: Zeteo does not read Tereo's reporting lines yet, and a rule using it is refused. Rules do not follow relations.

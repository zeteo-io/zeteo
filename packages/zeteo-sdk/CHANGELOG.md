## 0.1.0 (2026-11-20)

### 🚀 Features

- Dashboards: a dashboard is a grid of panels, each a saved query shown as a chart, a stat or a table, with saved panels to reuse a chart on many dashboards. Dashboards and saved panels are shared with users and groups, copied and transferred; a saved query's owner switches "Available for dashboards" on for others' panels. Every viewer runs every panel with their own grants, over a time range built from relative dates in the query language, as a stream of one line per panel with a short Redis cache (`DASHBOARD_CACHE_TTL_SECONDS`) and a recording window (`DASHBOARD_RECORD_WINDOW_MINUTES`) that records a dashboard's runs once per viewer per query. `/v1/dashboards`, `/v1/saved-panels`, `GET /v1/saved-queries?scope=available`, `GET /v1/saved-queries/{id}/dashboards`, the permissions `zeteo.dashboards.read` and `.write`, MCP tools for dashboards and saved panels, Dashboards, a display mode for wall screens and admin pages in the UI. SDK: `dashboards` and `savedPanels` calls. ([#13](https://github.com/zeteo-io/zeteo/pull/13))
- Uploads: a user with `zeteo.uploads.write` uploads a CSV or Excel file, previews and corrects it, and gets an `upload` source they own, stored in Zeteo's Postgres and queried through a read-only reader role (`UPLOADS_READER_URL`, off while unset). Owners grant, declare relations, describe, re-upload, retype, transfer and delete. Changes are audited under the sources' events with `type: "upload"` in the metadata: `zeteo.source.created`, `.updated` and the new `.deleted`, `.transferred`, `.tables_added`, `.table_reuploaded` and `.table_removed`. One sources API: `/v1/sources` serves database and upload sources alike (`POST` with `type: "upload"`, `DELETE`, `POST …/transfer`, `POST …/tables`, `PUT` and `DELETE …/tables/:tableId`, `PATCH …/columns/:columnId` for upload sources; `409 not_an_upload_source` on a database, and `409 not_a_database_source` for an upload source's archive, test, refresh, settings or schemas), its list filters by `type` and `owner_id` (`owner_id=me` for an owner holding only `zeteo.uploads.write`), and staging is `POST /v1/uploads` and `DELETE /v1/uploads/:uploadId`. The source view gains `share_count`, and an upload source's `size_bytes` is what it stores; tables gain `row_count` and `last_loaded_at`, columns `original_name`. The `UPLOAD_*` limits (bytes, rows, columns, quota, unconfirmed uploads and uploads in flight per user, xlsx workbooks read at once), start-up checks of the reader URL, the database version and Zeteo's `CREATE` privilege, "My sources" in My Zeteo, and one source page for every source (`/sources/:id`: Overview, Tables, Relations and Shared with, an Edit dialog for the settings, a back link to where it was opened from). Database sources get a size: `size_bytes` and `size_measured_at` on the source, the bytes on disk of the tables in its schemas, measured at each catalogue refresh (on Azure SQL it needs `VIEW DATABASE STATE`; a refresh that cannot read it keeps the last value), and each table an estimated `row_count` from the database's statistics (Postgres `reltuples`, or the live-row count for a table never analyzed; SQL Server `sys.partitions`), kept when a refresh cannot read them. An upload source's `last_refreshed_at` is its last load. SDK: the upload-source calls on `sources` (`create` with `type: "upload"`, `delete`, `transfer`, `addTables`, `reuploadTable`, `removeTable`, `updateColumn`), `uploads.create` and `uploads.discard`, the list's `type` and `owner_id`, and `size_bytes`, `size_measured_at` and `share_count` on `Source`. Every "who" filter in the admin UI is one searchable list of the whole directory, from the new `GET /v1/principals/all` (`zeteo.grants.read`) and `GET /v1/me/principals/all` (`zeteo.data.read`, the people and groups one may share with): `{ data, truncated }`, at most 5000 users and 5000 groups; SDK `principals.all()` and `me.allPrincipals()`. ([#14](https://github.com/zeteo-io/zeteo/pull/14))
- Google Sheets and merged tables in upload sources. There is one upload source type, `upload`, and each table has an origin: a file, a Google spreadsheet tab (with its spreadsheet, tab id and tab title) or a merged table, so one source mixes them. Add data and Add tables take a file or any spreadsheet link (`POST /v1/uploads/links` with `{ url }` or `{ source_id, url }`; with `source_id`, a tab that is already a table of that source is marked `already_added`); re-upload is for file tables only. An admin saves the Google service-account key under Connections (`GET` and `PUT /v1/connections/google`, sealed, checked with Google before saving). First claim wins per spreadsheet: it backs tables in at most one source, claimed when a source first gains one of its tabs and released when the source is deleted or its last non-removed table of it is removed (`sheet_in_use`, which never names the owner). Sheets tables sync on one interval per source (15 to 1440 minutes, default 60) or on Sync now (`POST /v1/sources/:id/refresh`, once a minute); each table loads in its own transaction, so one failure never holds back the others, and a failed table keeps its last good data and records `sync_error` for the owner. A source shows `sync` (`interval_minutes`, `last_attempt_at`, `failing`, `stale`), and tab titles refresh on sync. Merged tables (`POST /v1/sources/:id/merged-tables`, `PUT .../tables/:tableId/merged`, `GET .../merged-tables/columns`) stack two or more tables of a source as a live view with a label column, per-member labels, a chosen union of columns (disagreeing types become text, a missing column is NULL), warnings for members that go missing, and their own grants. Values load with Sheets' types and number formats in the sheet's time zone. New error codes: `invalid_sheet_link`, `sheet_in_use`, `sheet_not_accessible`, `google_not_configured`, `google_key_rejected`, `google_unavailable`, `google_sign_in_failed`, `tab_already_added`, `not_a_file_upload`, `not_synced`, `sync_too_soon`, `nothing_to_sync`, `table_in_merged_table`. The header-row suggestion changes for CSV and xlsx files too: a label row under a sparse banner is now suggested as the header. UI: Connections, an Origin column (Google Sheet or File Upload, with the tab), an Upload Sources tab listing a source's files and spreadsheets (in place of the overview's Google Sheets card), tabs already in the source marked Added, Add tables from a file or any sheet, Add merged table and its editor, a Sync failing badge, Sync now (only for a source with Sheets tables). SDK: the Google connection, sheet-link, merged-table calls and the origin and sync fields. BREAKING: the catalogue's `last_synced_at` is now `last_loaded_at`, and so are MCP `list_tables`' and `describe_table`'s; a file upload's owner calling `POST /v1/sources/:id/refresh` now gets `409 nothing_to_sync` instead of `403` when the source has no Sheets table; `POST /v1/sources/:id/refresh` may return a `SyncSummary` and is `429 sync_too_soon` within a minute; the refresh job now checks every 5 minutes. ([#18](https://github.com/zeteo-io/zeteo/pull/18))
- Measures and the calendar: a measure is a named, described aggregate on one table of a source (`paid_revenue`), expanded by the planner into any query as `{ "measure": name }`, with the query's filters and grouping applying to it and visible only to callers granted every column it reads. `/v1/sources/{id}/measures` (list, with whether the caller may edit them and manage their editors, create, get, change, delete, `preview` of a draft with the run entry point `measure_preview`) and `/v1/sources/{id}/measure-editors`; changes need `zeteo.measures.write` (on `zeteo_admin` and `zeteo_user`) and a place on the source's editor list, and a save that would break a measure using it is refused with `measure_in_use`. One calendar per install (`GET` and `PUT /v1/calendar`, `zeteo.calendar.write` on `zeteo_admin`): working days, holidays, fiscal year start month and the time zone that relative dates follow (`UTC` or a region name such as `Europe/Paris`; `CET`, `EST5EDT` and other names without a "/" are refused). The query language gains `case`, date arithmetic (`dateAdd`, `dateDiff` down to whole seconds, `datePart`, date and relative literals), business-day functions, and `fiscal_quarter` and `fiscal_year` buckets and relative units. `GET /v1/catalog`, MCP `describe_table`, `list_tables`, `list_sources`, the per-caller instructions and `query_guide` show and explain measures. A gauge chart for dashboards. New errors `measure_in_use`, `measure_needs_single_rows`, and the measure planner errors. The admin UI gains a Measures tab on a source (JSON editors with live validation, Preview, editors) and a Calendar page. Metrics and fixed measures: a measure may be `fixed` (one value that ignores the query's filters, usable from any table and as a comparison value in `where`, `having` and `case`) and may name a `date_column`; a metric is a named formula over measures of different tables of one source (`/v1/sources/{id}/metrics`: list, create, get, change, delete, `preview`, with the measures' editors and permissions; `measure_in_use` now also lists dependent metrics as `dependents`). A second query shape, `{ "metrics": [...], "bucket"?, "range"? }`, lines each measure up per period by its own date column, over HTTP, saved queries, exports, dashboards (panel time column `"range"`) and MCP, whose catalogue tools, `query_guide` and `preview_panel` cover metrics and fixed measures. Business days over columns at any grain, read in the calendar's time zone and the same on both engines: `businessDays`, `businessDaysBetween`, `businessDaysIn` (week to fiscal year), `businessDaysInMonth`, `businessDaysElapsed` and `businessDaysRemaining` with a unit, `addBusinessDays`, `datePart` `business_day`, the `isBusinessDay` filter operator, and `businessDaysInPeriod` in a metric's formula. Buckets and `datePart` read a timestamp as its date in the calendar's time zone too, and a bucket (a metric query's `period` included) is the first day of its period, typed `date`, so a range and its buckets agree on each instant's day. MCP tools let a source's measure editors list, preview, create, change and delete its measures and metrics (`list_measures`, `preview_measure`, `create_measure`, `update_measure`, `delete_measure` and the same for metrics), by source slug and name, under the API's rules. The admin UI gains a Fixed toggle and a Date column, measure and metric forms as pages of their own, and a Metrics tab; the Calendar page puts holidays in a table with an Add holidays dialog (row by row or pasted) and saves only on changes. Not included: filters on non-date dimensions in metric queries, metrics using metrics, and business hours. SDK: `measures` (`list`, `create`, `get`, `update`, `delete`, `preview`, `editors`, `replaceEditors`) and `calendar` (`get`, `replace`) calls, and `metrics` (`list`, `create`, `get`, `update`, `delete`, `preview`) calls, and the query types of the business-day forms (`PeriodUnit`). ([#19](https://github.com/zeteo-io/zeteo/pull/19))
- Queries can calculate: `{ calc, as }` select items and expression arguments to sum, avg, min and max. ([#10](https://github.com/zeteo-io/zeteo/pull/10))
- Discovered relations are renamed at the next refresh of each source: a foreign key to a table that has no other key to the same table is named after the target table (`customers`, not `customer`), and keys named by their column lose the table's column prefix and one key suffix. Queries and declared joins that use the old names must change. `PATCH /v1/sources/{sourceId}/relations/{relationId}` (SDK: `sources.relations.update`) renames a relation; a renamed discovered relation keeps its name across refreshes. ([#10](https://github.com/zeteo-io/zeteo/pull/10))
- Saved queries: a user keeps a query under a name, runs and exports it, shares it with users and groups, copies it and transfers it, and a recipient runs it with their own grants only. `/v1/saved-queries`, `GET /v1/me/runs`, `GET /v1/me/principals`, the permissions `zeteo.saved_queries.read` and `.write`, MCP tools for saved queries, "My Zeteo" and a Saved queries section in the admin UI. SDK: `savedQueries` and `me.runs` calls. ([#12](https://github.com/zeteo-io/zeteo/pull/12))
- The source types gained `description`. ([#15](https://github.com/zeteo-io/zeteo/pull/15))
- A per-source join limit, `max_joins` (1 to 8, default 4), set on create and update and reported by the source, the catalog and MCP `list_sources`; a query over it is `422 too_many_joins`. ([#10](https://github.com/zeteo-io/zeteo/pull/10))
- SDK: `me` and `principals` calls. zeteo: `GET /v1/me`, principal search and lookup, serving the admin UI's build, a content security policy. ([#7](https://github.com/zeteo-io/zeteo/pull/7))
